# Build Tool Rule

This is a **multi-module Eclipse workspace built with Ant**, targeting **Java 8** on a classic Java EE (EJB 2.x/3.x) application server. There is no Maven, no Gradle, and no wrapper script. Never introduce one.

## Hard Rules

1. **Never add a `pom.xml`, `build.gradle`, `build.gradle.kts`, or any Maven/Gradle wrapper.**
   Each module is a standalone Eclipse project (`.project` / `.classpath`) with its own `build.xml`. Do not try to unify modules under a single Maven/Gradle reactor — that is a different build model than the one this codebase uses.

2. **Treat each top-level folder as an independent module with its own classpath.**
   A module's source roots are declared in its `.classpath`, not inferred from convention — common roots are `ejbModule/`, `src/`, `src.api/`, `src.core/`, and `test/`. Before adding a new class, check the module's `.classpath` to see which root it belongs under; do not invent a `src/main/java` layout that the module doesn't use.

3. **Dependencies are vendored jars committed to each module's `lib/` folder — there is no dependency manager.**
   A module depends on a library by having the `.jar` physically present under its `lib/` directory and referenced as a `classpathentry kind="lib"` in `.classpath`. There is no BOM, no version catalog, and no transitive resolution — every jar a module needs must be present locally or reachable through a project reference to another module.

   ```
   # ✅ Correct — add the new jar to the module's lib/ folder,
   #    reference it in .classpath, and force-add it to git
   #    (the top-level .gitignore ignores *.jar by default)
   git add -f lib/some-library-1.2.3.jar

   # ❌ Wrong — do not add a dependency as a coordinate in a pom.xml/build.gradle
   # that does not exist in this build
   ```

4. **Never upgrade a vendored jar's version without checking every module that references it.**
   Several modules may point at the same library jar independently (e.g. each has its own copy or its own `lib/` entry). Changing one module's jar does not change another's — verify project references and other modules' `lib/` folders before assuming a version bump is workspace-wide.

5. **Compile against Java 8 — never use a language feature newer than Java 8.**
   Every module's `.classpath` pins `JavaSE-1.8` as the JRE container and `1.8` as source/target compliance in `org.eclipse.jdt.core.prefs`. This means **no** `var`, **no** records, **no** sealed types/interfaces, **no** pattern-matching `switch` expressions, **no** text blocks, and **no** `Stream.toList()` / `List.of()` / `Set.of()` / `Map.of()` (all introduced after Java 8). Lambdas, streams, `Optional`, and the `java.time` API are available and should be used.

6. **Packaging is done with Ant, invoked per module.**
   A module that produces a jar/EAR artifact declares a `dist` (or similarly named) Ant target in its `build.xml`, built from the Eclipse-compiled `.class` files under `bin/`. Run it with:

   ```bash
   ant -f <module>/build.xml dist
   ```

   Do not invent a Maven-style `package`/`install` lifecycle — there isn't one.

7. **Never commit `bin/`, `build/`, or other compiler output.**
   These are generated by the Eclipse/Ant build and are git-ignored. If you find them already tracked, don't assume that's intentional — ask before changing `.gitignore` behavior.

## Why

This codebase predates Maven/Gradle-based dependency management and still targets a Java EE application server whose tooling expects an Eclipse-managed workspace. Introducing a modern build tool would not actually resolve the module's dependencies (they live as committed jars, not coordinates) and would create a parallel, inconsistent build that nobody runs in practice. Working within the existing Ant + Eclipse model keeps changes buildable and deployable the same way the rest of the codebase is.
